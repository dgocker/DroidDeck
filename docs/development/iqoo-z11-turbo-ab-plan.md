## 2. Что исправлено и почему

### DD-03 — fence и command buffer, которые ещё держит GPU (`12decf2`)

- **Было.** Четыре пути в `vk_present.c` ждали свою работу на GPU не больше секунды:
  - копия в слой;
  - effects-pass слоя;
  - чтение курсора;
  - очистка letterbox-изображения.

  При тайм-ауте функция возвращалась, а следующий вызов делал `vkResetFences` и
  `vkResetCommandBuffer` на ещё исполняемых объектах. Кроме того, изображение, уничтоженное в этот
  момент, освобождалось прямо под работающей копией. Это нарушения
  VUID-vkResetFences-01123, -vkResetCommandBuffer-00045 и -vkDestroyImage-01000, то есть
  неопределённое поведение драйвера.
- **Стало.** Успешный `vkQueueSubmit` с общим fence помечает работу «в полёте». Пометка снимается,
  когда ожидание или `vkGetFenceStatus` видят fence сигнальным.
  - Пока работа в полёте, все пути, которые пишут в слот 0, пропускаются без ожидания: кадр, копия
    в слой, effects-pass, чтение курсора.
  - Копия в слой проверяет это **до** взятия слота пула, чтобы release fence дисплея остался при
    слоте.
  - Уничтожаемые в это время изображения откладываются и освобождаются, когда работа завершилась.
  - Потеря устройства обрабатывается как раньше: вывод останавливается, отложенное освобождается сразу.
- **Тайм-ауты не увеличены.** Работа, которая укладывается в срок, идёт ровно прежним путём: те же
  submit'ы и ожидания, ни одного вызова `vkGetFenceStatus`.
- **Тест.** Настоящий `vk_present.c` работает против фейкового устройства, которое падает на
  запрещённых сбросах и уничтожениях. Исходный код падает на второй копии после тайм-аута
  (воспроизведено). Новый проходит 4 сценария, в том числе под ASan/UBSan.

### DD-04 — потеря ввода при переполнении pipe (`cc3d00f`)

- **Было.** Клавиши, кнопки, касания, движения и тики vsync шли в один неблокирующий pipe примерно
  на 3 200 сообщений, а ошибка записи игнорировалась. Долгая остановка потока композитора теряла
  события, включая отпускание клавиш: клавиша «залипала».
- **Стало.** `input_queue.c` — упорядоченное переполнение за pipe.
  - Если в переполнении уже что-то ждёт, всё последующее встаёт за ним.
  - Читатель забирает переполнение только после последней проверки pipe под той же блокировкой.
  - Движения указателя и одного пальца сливаются с предыдущим движением; относительное движение и
    колесо суммируются. Тик vsync хранит только последнее время.
  - Сверх 4096 сообщений несливаемое отбрасывается, но **учитывается**: каждые 10 с пишется строка
    `input`, если pipe хоть раз переполнялся.
- **Тесты.** Пять сценариев, включая 4 писателя против 1 читателя. Многопоточный тест нашёл гонку
  переупорядочивания в первой версии; она исправлена до коммита. ThreadSanitizer и
  AddressSanitizer чистые.

### DD-02 — оценка периода vsync (`3f0ab28`)

- **Было.** Период для release-пейсинга (без лимита FPS игре возвращается один буфер за период) был
  EMA по времени, когда поток композитора *обработал* тик, с отбросом интервалов меньше 3 мс. Поздно
  обработанный тик учитывался, а ранний следующий отбрасывался, поэтому оценка росла.
  В синтетическом потоке 144 Гц, где каждый пятый тик обработан на 4 мс позже, она сошлась к
  **8,15 мс вместо 6,94 мс**. Это ограничивает игру без лимита примерно 122 кадрами/с.
- **Стало.** Используется `frameTimeNanos` Choreographer, временная метка vsync, которая и так
  приходила в каждом тике, но не использовалась. Пропущенный тик удлиняет интервал на целое число
  периодов, поэтому период — минимум последних 32 интервалов (`vsync_period.c`).
- **Тесты.** Поздняя обработка (включая демонстрацию дрейфа старой оценки), пропуски, смена режима
  60→144→120, паузы и неверные метки.

### Номинальная частота на каждую сессию (`5ab8e15`)

Композитор живёт весь процесс приложения. Частоту панели он узнавал один раз — при первом старте.
Размер выхода при этом уже обновлялся на каждую сессию.

`PerfMode` выбирает режим дисплея по лимиту FPS каждой сессии: без лимита 144 Гц, с лимитом
60 — 120 Гц. Если между сессиями сменился лимит, композитор продолжал сообщать старую частоту в
`wl_output` и в каждом `wp_presentation` feedback, хотя gamescope (`-r`) и панель уже работали на
новой.

Теперь частота задаётся вместе с размером перед каждой новой сессией и никогда во время сессии.

### Layer-режим для SDR (`aaf6adf`)

Layer-режим ставит полноэкранную игру на собственный слой дисплея. Тогда масштабирование на панель
делает дисплей, а GPU не копирует каждый кадр в swapchain размером с панель. Раньше режим включался
только с HDR. Теперь строка в `droiddeck-env` включает его и для SDR:

```
DROIDDECK_WAYLAND_ZERO_COPY=1
```

- **По умолчанию выключено:** без строки SDR остаётся на copy path. HDR держит режим включённым,
  что бы ни было в файле.
- **Все фолбэки layer-пути прежние.** Кадр, который слой взять не может, копируется как раньше:
  - frame generation;
  - окно над игрой, когда второй слой дисплею не по силам;
  - на устройстве нет слоя вовсе.
- Причина выбора пишется в `wayland.log`: `layer mode on: …` или `layer mode off: …`.
- **Жизненный цикл, проверенный по коду** (он не менялся, только впервые доступен в SDR):
  - release fence'ы `ASurfaceTransaction_setOnComplete`;
  - пул слотов;
  - смена Surface — `sc_layer_window_gone`;
  - поворот — `vkp_surface_rotation_degrees` и `sc_layer_overlay_affordable`;
  - resize — `check_surface_changed`;
  - сворачивание — без окна идёт `pace_without_output`;
  - отсутствие HWC-слоя — `sc_layer_available()`, и тогда `banner_ahb_v1` не объявляется.

### Политика частоты дисплея (`b118399`)

Логика `PerfMode` перенесена без изменения поведения в чистую функцию `DisplayModePolicy.pick`:

- кандидаты — только режимы текущего разрешения;
- с лимитом — самый быстрый режим, на который лимит делится нацело;
- иначе (или без лимита) — самый быстрый.

Поведение на панели 60/90/120/144 Гц по тестам:

| Лимит FPS | Выбранная частота | Обновлений на кадр |
|---|---|---|
| 30 | 120 Гц | 4 |
| 40 | 120 Гц | 3 |
| 45 | 90 Гц | 2 |
| 60 | 120 Гц | 2 |
| 90 | 90 Гц | 1 |
| 120 | 120 Гц | 1 |
| выкл. | 144 Гц | — |

Панель без 120 Гц и режимы 59,94/119,88 Гц тоже покрыты. Строка `perf:` в `app.log` теперь
перечисляет режимы панели, например
`display 144 → 120 Hz (mode 3; offers 60/90/120/144 Hz, cap 60 fps)`.

Лимит фиксируется при старте сессии; механизма смены посреди сессии в приложении нет. Тест
`aNewCapIsAppliedFromWhereverThePanelIs` проверяет повторное применение из любого предыдущего
режима. Частота дисплея меняет, когда кадр может быть показан, а не скорость CPU/GPU.

### Измеримость (`d4c1574`, `12decf2`, `3f0ab28`, `db1569a`, `fc3dd0f`)

- **Строка `pacing`** (каждые 10 с, только когда игра присылала кадры), по показателям:
  - интервалы между commit — темп, в котором игра (через gamescope) отдавала кадры. Это **не** FPS
    рендера игры: commit идёт после gamescope;
  - интервалы между сценами, впервые показавшими новый кадр игры, — уникальные показанные кадры.
    Они отдельны и от FPS игры, и от частоты панели;
  - число кадров, заменённых до показа (never shown);
  - задержка commit→present;
  - номинальная частота панели, измеренный период vsync, лимит FPS, состояние layer-режима.
- **Строка `perf`.** Добавлены счётчики «GPU waits timed out / uses skipped / destroys deferred».
  Время `render_scene` и ожидания fence там было и раньше. Активный путь виден по счётчикам copy,
  zero-copy и layer copy.
- **Строка `input`** — только при переполнении pipe.
- **Строка `graphics profile for app N`** в `session.log` при каждом запуске игры. В ней
  эффективные `TU_DEBUG`, ICD-драйвер, FEX, DXVK/VKD3D и `DROIDDECK_FORCE_SSBS` после всех профилей.
- **`tools/pacing_report.py`** сводит прогоны в таблицу с пропуском прогрева.

## 5. A/B-проверка на iQOO Z11 Turbo

### 5.1 Сборка и установка

- Сборка: `tools/build_local.sh` (Docker, Java 17, SDK/NDK, Rust, `zstd`). Либо артефакт
  `droiddeck-apk` из CI после push этой ветки; push не выполнялся — нужно ваше разрешение.
- Установка: `adb install -r app/build/outputs/apk/release/app-release.apk`. В A и B используйте
  **один и тот же** вариант пакета: `com.droiddeck.launcher` и «бенчмарк»-имена из
  `tools/release/variants.txt` могут получать разные режимы производительности OEM.

### 5.2 Условия — одинаковы для A и B

- Одна сборка и коммит, одна версия рантайма. Одни Proton, DXVK, VKD3D, драйвер (Auto или выбранный).
- Одна игра, версия, настройки графики, сохранение и сцена (маршрут или бенчмарк игры).
- Одно разрешение сессии; по умолчанию 720p — запишите, что выбрано.
- OriginOS: тот же режим производительности; яркость 50 %; авиарежим; заряд > 50 %; без зарядки;
  комната 22–26 °C.
- Прогрев 5 мин (первые 30 окон отбрасываются `--skip 30`), затем 20 мин записи.
- Не меньше трёх прогонов на вариант, чередуя A, B, A, B, A, B. Между прогонами остывать до
  исходной температуры: `adb shell dumpsys thermalservice` до и после.
- Сбор: **Share logs** (Setup или дровер сессии) → zip → из папки сессии взять `wayland.log`,
  `session.log`, `app.log`, `device.txt`.

### 5.3 Эксперименты — по одному параметру

**E1. Copy path против layer-режима (SDR).**
- A: файла нет (или `DROIDDECK_WAYLAND_ZERO_COPY=0`).
- B:
  ```sh
  echo DROIDDECK_WAYLAND_ZERO_COPY=1 > droiddeck-env
  adb push droiddeck-env /sdcard/Android/data/com.droiddeck.launcher/files/droiddeck-env
  ```
  Затем полностью перезапустить сессию.
- Проверка, что B действительно B:
  - `wayland.log: layer mode on: DROIDDECK_WAYLAND_ZERO_COPY=1 …`;
  - в `perf` растут `zero-copy` или `layer copy`, а не `copy`;
  - в `pacing` стоит `layer mode on`.
- Смотреть: shown p95/p99, never shown, `render_scene`, `fence wait`, температуру и разряд за 20 мин.

**E2. 144 Гц против 120 Гц для игры на 60 fps.**
- A: лимит FPS выкл.
- B: лимит 60 (Settings → режим → FPS limit).
- Проверка: в `app.log` строки `perf: display … → … Hz (… offers …)`; в `pacing` поля
  `panel … Hz nominal` и `fps limit`.
- Смотреть: интервалы shown. На 144 Гц ожидается смесь 13,9/20,8 мс, на 120 Гц — ровные 16,7 мс.
  Это проверяемый механизм, а не обещание FPS.

**E3. `TU_DEBUG=sysmem` против выбора Turnip.**
- A: по умолчанию — `sysmem` на всю сессию.
- B: Game environment → выбранная игра → `TU_DEBUG` → **Remove**. Так меняется одна переменная и
  только у игры; UI Steam остаётся на sysmem.
- Проверка: `session.log: graphics profile for app N: TU_DEBUG=-` в B и `TU_DEBUG=sysmem` в A.
- Признаки нестабильности: GPU hang или `DEVICE_LOST` в `wayland.log`, артефакты, вылет игры.
- Откат: **Use Default** или **Reset game profile**.

**E4. Force SSBS (ядра Oryon).**
- A: выкл.
- B: Game environment → игра → `DROIDDECK_FORCE_SSBS=1`.
- Проверка: `droiddeck-game-env: force SSBS on` и `DROIDDECK_FORCE_SSBS=1` в строке профиля.

### 5.4 Профили GPU — что фиксировать для каждого

| Поле | Откуда |
|---|---|
| GPU (модель, chip id) | `device.txt`: `KGSL gpu_model`, `KGSL chip id`, `GPU` |
| Драйвер композитора (bionic) | `device.txt`: `Display driver (chosen)`, `name / version` |
| Драйвер рантайма (glibc) | `device.txt`: `Linux driver`; в строке профиля — `VK_DRIVER_FILES` |
| Переменные окружения | `session.log`: `graphics profile for app N: …` |
| Backend | Proton (`droiddeck-proton:`), `DXVK_CONFIG` / `VKD3D_*` в строке профиля |
| Признаки сбоя | `wayland.log`: `DEVICE_LOST`, `GPU waits timed out`; падения игры в `session.log` |
| Возврат | E1: удалить строку из `droiddeck-env`; E3/E4: Use Default; E2: вернуть прежний лимит |

Профиль не меняется по одной модели GPU: каждый вариант проверяется на устройстве.

### 5.5 Сводка

```sh
python3 tools/pacing_report.py --skip 30 A1/wayland.log B1/wayland.log A2/wayland.log B2/wayland.log A3/wayland.log B3/wayland.log
```

## 7. Только на физическом устройстве

1. Собрать APK и прогнать его на iQOO Z11 Turbo. Сохранить первый `device.txt`:
   - `KGSL gpu_model` — 829 или 840;
   - драйверы;
   - `== kernel: page size` — 4 или 16 КБ;
   - режимы панели из строки `perf:`.
2. Проверить, что новые нативные пути работают в живой сессии:
   - строки `pacing` и `input` в `wayland.log`;
   - нет `GPU waits timed out` в обычной игре;
   - после сворачивания и возврата нет залипших клавиш.
3. E1 (layer SDR) на сценариях: полный экран; оверлей Steam поверх игры; поворот; PiP; смена Surface;
   эффекты экрана; frame generation (должен уходить на copy path); выход и возврат.
4. E2, E3, E4 — по 3 прогона на вариант по протоколу 5.2.
5. Длительный 30-мин прогон с лучшей конфигурацией: устойчивость частот и температуры, 1 % low по
   окнам.
6. Драйвер Adreno 829: 30 мин без GPU hang с выбранным Auto (WinNative Balanced) и с DD-Turnip,
   если он есть в списке.
7. Решение о значениях по умолчанию (layer SDR, `TU_DEBUG`, частота без лимита) — только по
   результатам п. 3–6 на нескольких играх.
